# AI Research Assistant

An educational Retrieval-Augmented Generation (RAG) project that answers
research questions from a private collection of indexed documents. The
assistant retrieves relevant source passages before asking an LLM to generate
an answer, helping keep responses grounded in the available research material.

## Problem Statement

Research information is often spread across multiple documents, making it
time-consuming to find relevant passages and connect them to a specific
question. A general-purpose LLM may also answer from its training data,
produce unsupported claims, or make it difficult to identify the sources behind
an answer.

This project addresses those problems by indexing research content in a local
vector database and using retrieval to provide the LLM with only the most
relevant context. The assistant is instructed to acknowledge when the indexed
documents do not contain enough information.

## Objective

The objective is to build a conversational research assistant that can:

- Ingest text documents and attach source metadata.
- Split large documents into overlapping chunks for better retrieval.
- Convert chunks into vector embeddings and persist them locally.
- Retrieve relevant passages using similarity search.
- Improve recall with optional multi-query retrieval generated by an LLM.
- Generate answers grounded only in the retrieved context.
- Maintain short-term conversation history per session.
- Return either a readable text answer or a structured response containing:
	- Answer
	- Confidence level (`high`, `medium`, or `low`)
	- Source documents
	- Key quotes
	- Suggested follow-up questions

## Project Processing Detail

### 1. Document Ingestion

Documents can be added through `add_documents`, `add_text`, or `add_texts`.
Each document can include a source name and additional metadata. The assistant
records the indexing time on every generated chunk.

### 2. Text Splitting

The `RecursiveCharacterTextSplitter` divides documents into chunks using a
default chunk size of 1,000 characters and an overlap of 200 characters. The
overlap preserves context between neighboring chunks and reduces the chance
that an important statement is split across retrieval boundaries.

### 3. Embedding and Persistence

Each chunk is converted into a vector using OpenAI's
`text-embedding-3-small` model. The vectors and metadata are stored in a
persistent Chroma collection named `research_docs` under `research_db/`.

### 4. Query Processing

When a user asks a question, the assistant:

1. Loads or creates the conversation history for the session.
2. Builds a retriever over the Chroma collection.
3. Uses basic similarity search by default, or `MultiQueryRetriever` when
	 advanced retrieval is enabled.
4. Retrieves relevant document chunks.
5. Formats the chunks with source labels for use as prompt context.
6. Sends the context, question, and the last 10 conversation messages to
	 `gpt-4o-mini`.
7. Stores the question and answer in the session history.

The prompt requires the model to use only the supplied context, cite the
sources it used, and state when the context does not contain an answer.

### 5. Response Formatting

The `ask` method returns a plain string response. The `ask_structured` method
uses Pydantic structured output and returns a `ResearchResponse` object. This
makes answer fields easier for other applications to consume programmatically.

### 6. Retrieval Comparison

The `compare_retrievers` method provides a side-by-side view of basic and
multi-query retrieval. It reports the number of returned chunks and the amount
of text that would be sent to the LLM, making retrieval behavior easier to
inspect while learning.

```text

															 |
															 v

										| AIResearchAssistant   |

											 |                 |
						 session history       query processing

											 v                 v
							+----------------+  +----------------------+
							| InMemory        |  | Retriever            |
							| Chat History    |  | Similarity /         |
							| per session     |  | MultiQueryRetriever  |
							+----------------+  +----------+-----------+
																							 |
																							 v
																	+------------------------+
																	| Chroma vector store    |
																	| research_docs          |
																	| ./research_db          |
																	+------------+-----------+
																							 |
												 relevant chunks + source metadata
																							 |
																							 v
																	+------------------------+
																	| Prompt construction    |
																	| context + history +   |
																	| question              |
																	+------------+-----------+
																							 |
																							 v
																	+------------------------+

																	+------------+-----------+

```

## Tech Stack

- **Python**: Application language.
- **LangChain**: Orchestration for prompts, retrievers, documents, chat
	history, and model integration.
- **OpenAI `gpt-4o-mini`**: Response generation and multi-query generation.
- **OpenAI `text-embedding-3-small`**: Document and query embeddings.
- **Chroma**: Persistent local vector database for embeddings and metadata.
- **Pydantic**: Validation and structured `ResearchResponse` output.
- **python-dotenv**: Loads configuration such as `OPENAI_API_KEY` from a
	`.env` file.
- **uv**: Python dependency and project runner used by the repository.

## Project Files

- `main.py`: Implements `AIResearchAssistant` and `ResearchResponse`.
- `data.py`: Provides sample research content and database seeding helpers.
- `test.py`: Contains smoke tests for ingestion, retrieval, sessions, and
	structured responses.
- `research_db/`: Persistent Chroma database created by the assistant.

## Configuration

Set the OpenAI API key in a `.env` file before running the assistant:

```env
OPENAI_API_KEY=your-api-key
```

The database is stored locally in `research_db/` by default, so indexed chunks
can be reused between executions.
